## 1. 決定

運用モデルと次の学習の初期値はv2.7.1を維持する。S09の2M・8周モデルは研究成果として保存する。
4M/10M化、2Mの無条件な追加反復、学習率の一括引き上げは当面見送る。
今回の結果は棋譜学習の限界を示していないが、同じ方法への長期計算の追加投資を積極的に支持してもいない。

次の順序は、**実装の小さな不整合を直す → 実用条件で不足している評価を補う → 同じ棋譜で損失関数を比較する → 有望な方式へ学習量を投入する**。
主実験は、現在の頻度付きpairwise RankNetと、全合法手の頻度分布を学ぶlistwise cross-entropyの比較とする。
HalfKPの構造・推論・教師の出所は維持し、静止探索末端のスコアから学ぶ。別のpolicy networkは作らない。

外部AIの評価値・解析PV・重み・訪問数は教師に使わない。KPP由来重みで初期化しない。
v2.7.1はscratch系統の初期値であり、その予測を正解にして回帰しない。
v2.5.0は比較相手。以前に許可された異系統対局の勝敗学習S10は条件付きの後続候補として残す。

既存`agreement`は、最頻棋譜手のスコアが最高スコアと等しい割合で、同点を含む。
実際に選択された着手の一致率とは厳密には異なる。またlossはコード上の重み和で正規化しており、頻度rootでは原則root平均になる。

clipは584/16,478更新（約3.54%）、feature最大更新差は0.001085。B2→B8も各phaseのlossは改善している。
一方、この変化だけで学習率が最適とも、過学習がないとも断定しない。

## 3. データと実装から分かった制約

### 頻度教師の情報量と品質

今回、凍結済みtrain JSONLを全件集計した。単なるmanifestの推定ではない。

| データ | root数 | 観測が1回だけ | 複数の着手が観測されたroot |
|---|---:|---:|---:|
| 元のS07 | 1,000,000 | 982,677（98.27%） | 6,239（0.624%） |
| 追加2012–2014 | 1,000,000 | 983,969（98.40%） | 5,046（0.505%） |
| S09合計 | 2,000,000 | 1,966,646（98.33%） | 11,285（0.564%） |

序盤だけでも複数着手は10,097/416,000（2.43%）。代表game_keyは元1Mで66,250、合計2Mで183,557。
これは集約後の代表棋譜数で、全寄与棋譜数の厳密な計数ではない。
大部分は一つの観測手を他の合法手より上にする学習であり、多数の棋譜から良い複数候補を選ぶ効果は限定的だった。
出現頻度は抽出済みレコードの頻度であって、全WDoor棋譜での頻度ではない。

追加コホートはrate記録なし。元1Mの両者rate>=2500と教師品質が揃っていない。
古い年代だから弱いと断定はできないが、これは品質一定の純粋なデータ倍増実験ではない。
今後データを増やす場合は、trainに許された棋譜で先に着手頻度を集約し、その後root数を絞る。
同一棋譜内の反復で票が増える影響も調べる。holdoutの着手を頻度集計へ混ぜず、浅い共有局面の衝突除外も維持する。
まず既存rootに対する頻度がどれだけ変わるかを測り、データ改善と目的関数変更は別の実験にする。

### 次の学習前に直す境界条件

`src/training_tools/halfkp_mmto_train.rs`の`add_pair_gradient`は、
`target_probability == 1 && pair_weight == 1`を旧MMTOの判別に使っている。
頻度データでも、合法手が2つ、観測手が1種類、その手がpairの先側なら同じ値になる。
この場合、評価時はRankNetなのに更新時は旧sigmoid目的となり、手の並び順によって勾配も変わる。
例えば差分0・tau=300では、本来の微分は−1/600、旧分岐では−1/1200になる。
テスト用`pair_loss`も同じ条件分岐なので、現状の有限差分テストだけではこの仕様不整合を検出できない。

データのlegal_moves_mean=2かつ単一教師手は33,148/2M（1.66%）。
これは候補となる入力の上限で、terminal除外や合法手の順序を考慮した実際の誤分岐数ではない。
全停滞の主因とは断定しないが、目的関数の種類を明示して修正し、2合法手・両順序・両手番のテストを追加する。
過去の重み・対局結果は削除せず、この不整合を含む実装で得た結果として残す。

### 実用対局と評価器を揃える

S09の`halfkp_promotion_match`は毎手`reset_for_independent_search()`を呼び、TT・手順履歴を消している。
USIの通常対局は局開始時に初期化し、その後は履歴を減衰させながら探索状態を引き継ぐ。
S08はUSI経由・最大depth32・投了あり、S09は直接呼出し・最大depth64・合法手なしまで続ける方式だった。
S09内では両者同条件なので比較は有効だが、S07/S08の56%と今回の56%を同一尺度の成長曲線にはできない。
「探索が十分優秀で、問題は重みだけ」とも今回の結果からは断定できない。

次の棋力評価は既存USI benchmarkを基準に統一する。同じbinary・設定・1 thread/側・5秒/手・先後交換・定跡なし。
最大depth等も事前固定し、完全な指し手列を保存する。S09のreportは勝敗・終了理由・手数を保存するが、全着手列は持たない。
既存100局をそのまま敗因解析できるものとは扱わず、次の対局から盤面・手順を辿れるようにする。
未完了だった浅い序盤からの50局と、既存の詰み・受け・駒損回避問題を補う。
固定問題は解答が確認できるものを使い、親の最善手との不一致をそのまま誤答にしない。

自動実行も最小修正が必要。S09 runnerには未定義`EVAL_DIR`、末尾の未定義`now`、
再実行時に完了済みの中間snapshotへ最終modelをコピーし得る分岐がある。
今回のA4/B2/B4/B8はmodel SHAと各metricの一致を確認した。現成果物の破損を意味しないが、修正前にrunner全体を再実行しない。

## 4. 次の主実験：選ぶ手に結び付く学習

現在は棋譜手と多数の代替手のpair損失を平均している。
本命の誤った1手が首位に残っていても、それ以外の手との差が広がれば平均lossは改善する。
今回のloss改善と対局結果の隔たりに対する仮説であり、原因が確定したという意味ではない。

比較候補では、同じ全合法手のqsearch末端スコアを手番側へ揃えて、
`p(move) = softmax(score(move) / 300)`、教師を`q(move) = count(move) / sum(count)`とし、
rootごとの`−sum(q * log(p))`を最小化する。高く評価してしまった手へ勾配が集中しやすい。
複数の棋譜手は頻度どおり扱う。これは着手分布であって勝率の予測ではない。
未観測手が必ず悪手という意味でもなく、教師の質・量の問題は残る。

これは既存の「一手後の静的評価にCEをかけた旧pilot」の再実行ではない。
現在のqsearch末端・各outerでの探索更新・頻度教師を維持する。新しいpolicy headや外部教師は不要。
RankNetとlistwiseの違いを小さく検証する提案で、将棋での優位性は未検証。

初回は次の2本に固定する。

- v2.7.1の同じmodel/AdaGrad状態から開始。S07のrate付き1Mから固定100k rootを取り、各8周。phase比率は20.8/55.2/24.0%。
- Aは境界条件を修正した現在のRankNet、Bは上記listwise。LR=1e-4、output比率0.1、tau=300、clip=1、12 workerを共通にする。
- rootのバッチ境界・正規化・更新回数を揃える。既存pair batch8192をlistwiseの8192 rootと取り違えない。損失の種類以外の変更は両run共通に記録する。
- 2/4/8周のmodelとoptimizerを保存し、対局候補は8周に事前固定。旧・新の両validで同じ評価指標を出す。異なる目的関数の生loss同士は比較しない。
- 共通指標は、実際に選んだ手の最頻手集合への一致、観測手集合への一致、選択手の教師頻度、上位3手が含む教師頻度、phase別成績。頻度指標自体を棋力とみなさない。
- 技術異常と基本戦術の明確な新規失敗は調査する。単発loss変動や旧親valueへの誤差で、予定した8周の対局候補を消さない。

新目的は安定したlog-softmaxを用い、両手番の有限差分、教師頻度との勾配一致、再開時の目的関数設定一致を確認してから実行する。
概算は1M・1周約20時間から、100k・8周で1本約16時間、2本で約32時間＋検証・対局。
これは見積もりであり、最初の25k rootで実測する。数分の試験を本学習と扱わない。
100k比較の不発は学習方式一般の否定ではなく、この予算で長期拡張を支持する根拠が得られなかった、と記録する。

### 実装・実行記録

- 実行定義: `scripts/run_halfkp_listwise_experiment.py`。状態・段階ログ・固定binary SHA・入力SHA・対局組・最終判断はrun配下に保存する。再開も同じcommandを使う。
  `python3 -u scripts/run_halfkp_listwise_experiment.py`
- 100k trainは序/中/終20,800/55,200/24,000 root。両方式は128入力rootごとに更新し、25k rootごとにcheckpointを確定する。2/4/8周のsnapshotは検証済み成果物を上書きしない。
- trainerの明示的な損失種類、新listwise目的、選択手に基づく頻度指標、読取専用`halfkp_frequency_evaluate`を追加。RankNetの報告損失も安定したlogistic式にしたため、極端なスコア差では旧報告の確率clipによる値と異なり得る。比較は同じ新評価器で行う。
- 再開時は目的・バッチ・LR等の設定指紋を検証する。旧checkpointは同じ実験として黙って再開せず、必要ならmodel/optimizerから別runを作る。中断outerの差分制限は開始時snapshotを基準にし、train指標が中断後の部分集計なら`train_metrics_start_root`を記録する。
- `scripts/check_halfkp_frequency_resume.py`で32 root・2周を実行し、両目的について4 root後の強制中断→再開と連続実行のmodel/optimizer SHAが一致。目的を変更した再開は保存物を変更せず拒否した。証跡は`s10-resume-check-20261025/report.json`。
- USI対局は2局単位で記録・再開し、完全な手順を残す。正常な開始局面・先後交換・終了理由を照合し、内部探索エラーや非有限scoreを正常対局に数えない。実エンジンの短時間2局で出力形式も確認済み。
- 固定問題は既存の証明付き詰み/受けvalidと合法局面の評価健全性に加え、両手番の単純な駒取り6題を使用する。後者は即時捕獲の診断であり、唯一の最善手・勝敗の数学的証明ではない。
- 無人でのR5拡張は保守的に、詰み/受けの解答数・判定可能数が親を下回らず、親が通った捕獲問題に新しい失敗がない場合に限定する。小さな低下も自動拡張を見送るが、方式の劣化確定とは扱わず、固定問題の報告を残して確認対象にする。
- 対局開始局面は学習開始前に固定。既存記録3,134開始commandを照合し、未使用のtaya command 1,348件から後続用100件を予約した。浅い50件は歴史棋譜testから別family・別盤面を選び、S07/S09 trainとの盤面非重複を確認した。全祖先重みにとって未学習の盤面であることまで証明したものではない。
- run名の`s10-listwise`は今回のR1–R5比較を指す。10/7計画の異系統勝敗学習S10は起動していない。runnerは条件付き1M確認までで終了し、リリースや新方式へは自動移行しない。

### 2026-10-26 停止原因の修正と再開

- 停止原因は固定問題の参照先選定ミス。`exact-pairs22k-v2/valid/pairs.hkcl`は廃止済みHKCL0002で、現readerが要求するHKCL0004と互換性がなかった。ヘッダーを書き換えて旧データを通す対応はしていない。
- 使用問題を既存の`exact-rank-v4-dev1k/valid.hkcl`へ変更した。HKCL0004・rule v3、攻撃500/防御500の1,000問題で、attackerの色と再検証可能な証明を保持する固定dev集合。学習への投入・教師の変更はない。
- 起動直後に両HKCL入力のmagic/version/次元/lineageを確認し、exactの攻守・rule v3情報も検査する。さらにnative auditで全レコードを読み、全proofを再検証してから評価へ進む。旧版や切れたmetadataを開始前に拒否するテストを追加した。

一次資料は2026-10-25に再確認した。

- [Hoki・KanekoのMMTO論文](https://www.jair.org/index.php/jair/article/view/10871)は、探索末端を使って棋譜の着手決定へ近付ける学習を扱う。現実装と原論文は同一ではない。探索と評価関数を一緒に検証する根拠とする。
- [RankNet著者の解説](https://www.microsoft.com/en-us/research/blog/ranknet-a-ranking-retrospective/)は、pairの順位改善と最上位の選択品質が一致しない問題を説明する。本repoでの原因確定ではなく、主実験を選ぶ参考。
- [Caoらのlistwise学習論文](https://www.microsoft.com/en-us/research/publication/learning-to-rank-from-pairwise-approach-to-listwise-approach/)は候補集合全体とtop-one確率を用いる学習を提案する。情報検索での結果を将棋の棋力向上保証として引用しない。本計画の教師は棋譜頻度にする。
- [Stockfishのfeature factorization解説](https://official-stockfish.github.io/docs/nnue-pytorch-wiki/docs/nnue.html#feature-factorization)は疎なHalfKP特徴を学習時に共有する手法を説明する。容量不足の証拠なしに今回追加する理由にはしない。
- [やねうら王の勝敗のみからの学習例](https://yaneuraou.yaneu.com/2017/06/20/従来手法に基づくプロの棋譜を用いない評価関数/)はS10の可能性を支持するが、局面規模・探索・評価関数が異なる。小さな勝敗pilotで同じ成果を期待する根拠にはしない。
