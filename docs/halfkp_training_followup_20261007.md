# v2.7.1後の重み学習計画

決定日: 2026-10-07。[9/29計画](halfkp_training_followup_20260929.md)の後続方針を更新する。
今回は計画策定。学習・棋譜生成・対局はまだ開始していない。

## 1. 決定

**本線はv2.7.1から、独立棋譜を増やした2M局面で現在の頻度付き順位学習を継続する。**
同じ1Mをさらに反復する小さな対照を置き、追加データの価値を確認する。
LR引き上げ、optimizer交換、巨大networkへの変更は今の第一選択にしない。

**次段はv2.5.0・v2.7.1の異系統対局から得る実際の勝敗を使う、小規模な補助学習。**
最新のユーザー提案により、v2.5.0を学習用対局の相手に使うことを計画へ追加する。
これは以前の「比較対局専用」からの変更であり、純粋な棋譜学習系統とは別runで記録する。
v2.5.0の重みで初期化せず、評価値・解析PV・訪問数の蒸留も行わない。
外部AIの評価値等を教師にしない制約は継続する。

優先順位は「独立データ拡張 → 異系統対局の勝敗による補助学習 → 診断に応じた探索末端/特徴共有の変更」。
棋譜学習の飽和はまだ確認できていないので、全面的な自己対局移行はしない。

## 2. 実験結果から判断できること

| 実験 | 結果 | 解釈 |
|---|---|---|
| S05: 250k×8 | v2.5.0に19勝31敗 | この条件では負け越し |
| S06: 250k×16 | v2.5.0に43勝57敗 | 反復だけで大幅改善した証拠はない |
| S07: 1M×8、v2.7.0 | v2.5.0に56勝44敗、paired 95%区間47–65% | 方向は良いが優位確定ではない |
| S08: 1M×16、v2.7.1 | v2.7.0に29勝21敗、区間44–72% | 追加反復に前進の兆候 |
| 同上 | v2.5.0に56勝44敗、区間46–66% | 勝ち越し。ただし大幅強化も統計的優位も未確定 |

S07/S08は異なる開始局面を含むため、同じ56%から「全く伸びていない」とも言えない。
S05〜S07はデータ品質・年代・抽出密度も異なり、局面数だけの因果効果を測った実験ではない。
過去のvalue回帰や実装不整合を含む実験を、現在の順位学習の失敗回数として合算しない。

同一S07 validで、outer8→12→16のlossは0.356321→0.351055→0.347186。
8→16は約2.56%改善し、序盤0.387733→0.372388、中盤0.340097→0.332138、終盤0.365981→0.362074。
一方、指し手一致率は26.10%→26.42%と約0.33ポイントの改善にとどまる。
損失の改善がそのまま実戦の手の改善になるわけではない。頻度教師には複数の正解候補があり、一致率100%も目標ではない。

outer16は入力1Mに対し処理967,065 root、terminal除外116,701、aborted23,416、loss寄与約850,364。
validのabortedは8時点274から16時点271で、発散を示す急増はない。
コード上、いずれかの合法手が詰み・反復の末端になるsoft-target rootは順位勾配から除外される。
終盤全体を同じ密度で学べているとは限らないが、この仕様を今回同時に変更する根拠はない。
`mean_regret_cp`も詰み等の固定値を含むため、その大きさだけで評価尺度の破綻と断定しない。

有力な制約は、独立棋譜の幅、模倣目的と実戦勝敗の差、qsearchだけで表現する静かな構想の限界。
どれが主因かは未確定。HalfKPの容量不足やLR不足を主因とする証拠もまだない。

## 3. S09: 2Mへの拡張を本線にする

### データ

- 現1Mを保持し、新しい棋譜から約1Mの新規局面を加える。train内の同一盤面は実着手頻度を再集約し、重複行で2Mを水増ししない。
- まず手元のWDoorアーカイブを使用する。2015–2017以外も候補にし、既使用棋譜の履歴と照合する。足りなければ追加年代を取得する。
- 両者rate下限2500を下回らず、年代別のrate・参加者・終局理由・独立game数を報告する。年代をまたぐ同じrateを同じ棋力と仮定しない。
- 最初はS07の序/中/終比率20.8/55.2/24.0%を維持する。2Mでは416k/1,104k/480kを目安とする。序盤比率の変更は別実験にする。
- 既存の1棋譜64 root上限を引き上げない。頻度集約の代表gameだけでなく、元の寄与game数と抽出密度も確認する。
- 全履歴のvalid/test・評価開始局面を保護する。splitはgame/familyで固定し、盤面衝突も除外する。頻度はtrain内だけから作る。
- 元1Mと新1Mを全体混合する。旧データの後ろに新データを連結するだけにはしない。
- 2Mに届かない場合は実件数を報告して追加棋譜を探す。rate低下・game上限引き上げを自動で行わない。

### 学習と比較

両runともv2.7.1の同一modelとAdaGrad状態から開始する。
feature LR=1e-4、output比率0.1、tau=300、clip=1、pair batch8192、qsearch上限2M、12 workerを維持。

| run | データ・追加提示量 | 役割 |
|---|---|---|
| A | 既存1M×追加4 pass | 同じ棋譜を反復する対照 |
| B | 新旧2M×2 pass、その後4/8 passまで保存 | 4M提示時点でAと比較し、主候補は8 pass |

AとBの2 pass時点は同じ4M入力提示量だが、勾配対象数・pair数・探索費用は完全には一致しないので併記する。
新データに対応するBの2 passだけで方式を棄却せず、正常なら8 passまで進める。
A/Bの4M提示時点では共通validと50局の直接比較を行い、方向を測る。ここで有意差を必須条件にしない。
旧valid固定12kと、新規gameから事前凍結する別valid12kを分けて評価し、phase別loss・一致率・除外率を記録する。
新validは過去全trainと照合する。旧validは既に何度も参照した開発集合である。

Bの4/8 passでmodel・optimizer・manifestを保存する。最終候補は事前指定した8 pass。
技術異常や明確な継続的劣化がない限り、単発loss変動・小標本の負け越しでは中断しない。
NaN、hash不整合、不正手、再開不整合は停止して原因を修正する。

S08実測は約20.4時間/1M pass。A約3.4日、Bの全8 pass約13.6日、合計約17日＋データ準備・対局が概算。
新データの探索難度によって変わるため、最初の25k処理後に実測で更新する。これは予約済み実行時間ではない。

### 実装上の最小作業

既存のaggregate/select、`halfkp_mmto_train`、paired-match、S08の保存手順を再利用する。
`--init-optimizer`は既に存在する。一方、`--resume`はdataset SHAを固定し、初期値には旧promotion registryの受理親検証がある。
従ってdatasetを書き換えたresumeや、v2.7.1をgen6と偽装する方法は使わない。
実装時は「元scratch系譜・S08完了bundle・公開重みSHA」を検証する研究継続の経路を最小限追加し、
新datasetのrunとして開始する。対局優位未確定とリリース済みを区別し、過去Gate記録は書き換えない。
検証対象はmodel/optimizerの対応、データ変更時の新run、途中再開時の設定一致。大規模な管理基盤は作らない。

## 4. 対局評価と拡張の分岐

B最終候補を、同一binary・各1 thread・両者5秒/手・先後交換で評価する。

1. 対v2.7.1を50局、対v2.5.0を50局。事前固定したtaya36開始局面を使い、局面一覧・SHA・使用履歴を保存する。
2. 序盤評価のため、学習/選択に使っていない浅い開始局面25組・50局を対v2.7.1で別集計する。互角中盤からの結果と混ぜない。
3. 固定した既存戦術/終盤問題も両モデルで確認する。S08eの完了証跡は今回未確認なので、完了済みとは扱わない。

50局はscreenであり、負け越しは劣化確定でも勝ち越しは優位確定でもない。
両比較相手に得点率54%以上（50局なら27点以上）、重大な終盤回帰なしを次段拡張の目安とする。
これは運用判断であり統計的証明ではない。有望なら候補を固定して独立100局でv2.7.1と確認する。
paired 95%区間を併記し、50%を含むなら優位未確認のまま記録する。勝つまで追加対局しない。
独立の未使用taya局面が不足したらその事実を記録し、確認用には別の未使用集合を用意する。

- **対局でも改善を支持:** 次は独立棋譜4M、8 passを基本候補にする。2Mの結果を見ずに10Mを作らない。
- **lossは改善、棋力は不明/停滞:** 以下S10を小規模で実施する。Bを研究候補として保存し、v2.7.1を維持する。
- **新validが悪化し旧validだけ改善:** 新規棋譜の品質・分布と過適合を先に点検する。
- **学習側も停滞:** 実効更新量・clip率・勾配・特徴出現数を確認する。LR不足が支持されるときだけ1e-4対2e-4の小規模比較を次の一変更にする。optimizerリセットは別の変更として扱う。

## 5. S10: 異系統対局を使うなら、勝敗による補助学習

系統が違うことは、異なる弱点を突き、棋譜に少ない自作モデルの到達局面を得る利点になり得る。
しかし、二つを対局させるだけでは重みは更新されず、互いの悪手を模倣しても強くなるとは限らない。
両者の評価値平均や、勝者の全着手を正解とする教師は採用しない。

最初のpilotは凍結したv2.5.0対v2.7.1で1,000局、500開始局面を先後交換する。
学習専用の浅い棋譜局面から開始し、まず1秒/手・各1 thread、少数の同時対局でCPU資源を固定する。
生成用openingは評価用と分離し、家族単位でtrain/validを分ける。途中でモデルを更新しない。
時間・局数は最初の100局で見積もる。生成コストを測らず1M局面生成には進まない。

各対局から序中盤を含む最大32局面を抽出する。上限32k局面であり、1,000局しか独立gameがないことを明記する。
両側・勝敗両方を使い、勝者だけを残さない。教師は実際に終局した勝敗のみ。
評価値による早期勝敗判定は使わず、時間切れ・異常終了・手数打切りを勝敗教師にしない。
drawは0.5を正しく扱える形式へ最小修正するか、pilotでは除外して件数を記録する。勝敗を捏造しない。

既存の独立WDL pool/hybrid経路を再利用する。終局結果は実際に出現したrootに付与し、
棋譜で指されなかった代替手のqsearch leafへコピーしない。実装済みのBrier補助損失を初期候補とする。
順位学習を主目的に残し、同じ初期値・データ・提示量で「棋譜順位のみ」と「順位＋対局勝敗」を比較する。
固定100kの棋譜root×4 passを初回規模とし、補助係数は各損失の平均化を確認したうえで、
訓練側小batchの勾配normが順位側の約10%になる初期値を一度決め、manifestへ凍結する。
この10%は最適値の主張ではなく、既存の棋譜知識を壊しにくくするpilot設定である。
比較は対v2.7.1・v2.5.0の双方と新しい開始局面で行い、v2.5.0への特化だけを成功としない。
1,000局pilotの不発は勝敗学習一般の不成立を意味しない。採用判断には独立対局が必要。

## 6. 新しい方法を採る条件

- 静かな序中盤で誤順位が集中し、qsearchと浅い通常探索の判断差が大きければ、固定100k rootで比較末端に通常探索を追加するA/Bを次候補にする。正解は棋譜手のまま。深くする費用と実戦への効果を測る。
- 稀な玉位置や未学習特徴へ誤りが集中するなら、訓練時だけ共通の駒特徴を持たせるfeature factorizationを優先する。出力時にHalfKPへ畳み込めるため、推論速度を保てる可能性がある。畳込み前後の一致検証は必須。
- 単なる停滞を理由に上記二つ、LR変更、新networkを同時に入れない。診断が支持する一変更を小規模比較してから拡張する。
